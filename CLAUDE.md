# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This repo is a Figma-exported frontend prototype ("SentiMark", a brand sentiment-analysis dashboard) plus a FastAPI/Firebase backend and one placeholder folder:

- `Frontend/` — the UI. React + Vite. Still reads entirely from local mock fixtures, not yet wired to `Backend/` (see Integration status below).
- `Backend/` — FastAPI + Firebase Admin SDK (Firestore). Data-layer only: no auth, no real sentiment computation yet.
- `Entreno/` — empty directory (presumably intended for ML/model training, nothing here yet).

There is no git repository initialized at the root. When work here needs version control, offer to `git init`.

## Commands

Frontend (from `Frontend/`):

```
npm i          # install deps (package-lock.json and pnpm-lock.yaml both present — prefer npm since package-lock.json is more current, unless the user says otherwise)
npm run dev    # start Vite dev server
npm run build  # production build (vite build)
```

There is no lint, typecheck, or test command configured — no `tsconfig.json`, no ESLint/Prettier config, and no test runner is wired up despite `.tsx` files (Vite/esbuild strips types without checking them). Don't assume `npm run lint` or `npm test` exist; check `package.json` before inventing a script.

Backend (from `Backend/`, Python 3.13 used during development):

```
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
python -m scripts.seed_firestore   # optional: loads the same fixtures mockData.ts has, into Firestore
uvicorn app.main:app --reload      # http://localhost:8000, docs at /docs
```

Requires a Firebase project with Firestore enabled and a service-account key saved at `Backend/serviceAccountKey.json` (gitignored — see `Backend/README.md`). No test suite yet.

## Architecture

**Everything lives in one component file**: [Frontend/src/app/components/Dashboard.tsx](Frontend/src/app/components/Dashboard.tsx). It's a single default-exported `Dashboard` component that owns all navigation state (`activeTab`, no router-driven sub-routes) and renders five inline panel components declared below it in the same file: `OverviewPanel`, `MentionsPanel`, `TrendsPanel`, `TopicsPanel`, `SettingsPanel`. There's also `NavItem` and `SentimentBadge` as local subcomponents. This is the pattern to follow when adding a new dashboard section — add a case to the `activeTab` switch and a new panel function — rather than introducing a separate routing/state library.

**Routing is a single catch-all route**: [Frontend/src/app/routes.tsx](Frontend/src/app/routes.tsx) defines one `react-router` route (`/` → `Dashboard`). Tab switching inside the dashboard is local `useState`, not URL-driven — there are no nested routes to update when adding a tab.

**Data is entirely mocked**: [Frontend/src/app/data/mockData.ts](Frontend/src/app/data/mockData.ts) exports the fixture arrays (`overviewMetrics`, `sentimentTrendData`, `sentimentDistribution`, `topicAnalysisData`, `recentMentions`) that `Dashboard.tsx` imports directly. There is no API client, no fetch/axios layer, no environment config for a backend URL. When wiring up real data, this is the seam to replace.

**UI kit**: [Frontend/src/app/components/ui/](Frontend/src/app/components/ui/) is a full shadcn/ui-style component set (Radix primitives + `class-variance-authority` + `tailwind-merge`) generated by the Figma/Make export. Most of these files are not yet imported anywhere in `Dashboard.tsx` — the dashboard currently hand-rolls its own markup/Tailwind classes rather than using these primitives. Prefer reusing an existing `ui/` primitive over hand-rolling new markup when extending the dashboard, but don't assume every primitive is already wired up or themed to match — check first.

**Styling**: Tailwind v4 via `@tailwindcss/vite` (no `tailwind.config.js` — v4 is CSS-config-driven). Tokens/theme live in [Frontend/src/styles/theme.css](Frontend/src/styles/theme.css) and [Frontend/src/styles/tailwind.css](Frontend/src/styles/tailwind.css); fonts in [Frontend/src/styles/fonts.css](Frontend/src/styles/fonts.css). The dashboard UI is in Spanish (labels, copy) — keep new UI copy in Spanish for consistency.

**Figma asset imports**: [Frontend/vite.config.ts](Frontend/vite.config.ts) has a custom `figmaAssetResolver` plugin that resolves `figma:asset/*` import specifiers to `src/assets/`. Do not remove the `react()`/`tailwindcss()` plugins even if Tailwind classes appear unused in a given file — the project comment explicitly notes both are required for the Figma "Make" export pipeline to keep working.

**Path alias**: `@` → `Frontend/src` (configured in `vite.config.ts`).

**Backend layout**: [Backend/app/main.py](Backend/app/main.py) wires up FastAPI + CORS and includes two routers: [Backend/app/routers/mentions.py](Backend/app/routers/mentions.py) (full CRUD on the `mentions` Firestore collection) and [Backend/app/routers/metrics.py](Backend/app/routers/metrics.py) (GET/PUT on four fixed documents in the `metrics` collection: `overview`, `sentiment_trend`, `sentiment_distribution`, `topics` — each storing an `items` array shaped exactly like the corresponding export in `mockData.ts`). [Backend/app/firebase.py](Backend/app/firebase.py) lazily initializes the Firebase Admin SDK via `GOOGLE_APPLICATION_CREDENTIALS` (see `Backend/env.example`). [Backend/scripts/seed_firestore.py](Backend/scripts/seed_firestore.py) is a one-off script (not imported by the app) that copies the current `mockData.ts` values into Firestore for local testing — keep it in sync manually if the mock shapes change.

**Integration status**: `Frontend/src/app/data/mockData.ts` has NOT been changed to call the backend — `Dashboard.tsx` still imports the static fixtures directly. Wiring the frontend to `Backend/`'s REST API (base URL, fetch layer, loading/error states) is unstarted work, not an oversight.
